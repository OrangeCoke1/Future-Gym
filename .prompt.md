# Task: Make the figure move in sync with the person in camera mode (reduce lag, add short-horizon prediction)

User report: "after the program recognises my movement the figure does it once, but it lags; when I squat it should squat at the same time — can it predict my movement?"

## Diagnosis (where the lag comes from)

1. **Replay view is lagging by design (the main cause of what the user describes).**
   `camView === 'replay'` plays the scripted exercise only after FIT emits `action_start` / `rep`
   (`fitEvents` → `replayAdd` → `RP.q`). A rep event fires at the *end* of a rep, so the figure is
   always ≥ 1 full rep (≈1–2 s) behind, and catches up at 1.8× speed when more than one rep is queued.
2. **Live view: One Euro filter is tuned for smoothness, not latency.**
   `oneEuro(minCut = 1.2, beta = 4)` in `src/pose/camera.js`. At 1.2 Hz the slow-motion time constant is
   1/(2π·1.2) ≈ 130 ms; a squat (~0.3–0.6 m/s) only raises the cutoff to ~2.4–3.6 Hz (≈45–65 ms lag).
3. **Live view: no interpolation/extrapolation between detections.** Detection runs per camera frame
   (~30 fps, lower on CPU); the render loop reuses the last filtered joints, so the figure steps and
   shows data that is on average another half frame old.
4. **Pipeline latency we can't remove:** camera exposure + capture (~30–60 ms) and Pose Landmarker
   *full* inference (~15–30 ms GPU, 60–150 ms CPU fallback).
5. **Ground smoothing** `ground.k = 1 - exp(-dt*6)` in live view (≈170 ms) delays the vertical drop of
   the whole body on a squat.

## Feasibility answer for the user

- Zero latency is physically impossible (camera + model ≈ 60–120 ms), but it can be made to *feel*
  in sync: tuning + 60–100 ms velocity prediction hides most of it.
- "Predicting the whole movement before it happens" is not possible from one camera; what is possible
  is phase-syncing the scripted animation to the person's live joint angle once the exercise is known.

## Plan

### Step 1 — Live view: low-latency filter + prediction (`src/pose/camera.js`)
- Retune `oneEuro` defaults: `minCut 1.2 → 2.0`, `beta 4 → 8` (keeps jitter low when still, much less
  lag when moving). Keep the filter function pure.
- Make `oneEuro` also expose the filtered velocity `dx` (return `{ x, dx }` internally, or keep the
  per-axis velocity on the filter object) so prediction can reuse it.
- In `camIngest`, store per joint the filtered position, its velocity and the detection timestamp
  (`cam.V[name]`, `cam.tDet`).
- New pure function `camPredict(cam, now, lead)` → joints extrapolated to `now + lead`:
  `J + V * clamp(now - tDet + lead, 0, 0.15 s)`, with velocity clamped to a max speed (e.g. 3 m/s) and
  the lead faded to 0 when the joint is not tracked/visible. Default `lead = 0.08 s`.
- `camSolve` reads from the predicted joints instead of `cam.J` (bone lengths are re-imposed by the
  retargeting, so overshoot cannot stretch limbs).

### Step 2 — Engine wiring (`src/engine/engine.js`)
- Live view: call `camSolve(camera.pose, S.action, now)` with prediction every render frame (this also
  gives smooth inter-frame motion at 60 fps).
- Live view ground: `ground.k` `6 → 20` per second so squats drop the body without the ~170 ms trail.
- Add a `S.camLead` setting (0 = off, default 0.08 s) and `setCamLead(v)` engine method, plus a
  console hook `stickman.setCamLead(ms)` for tuning on a real webcam (no UI change, avoids touching
  `CamPreview.vue`, which PR #1 is changing).

### Step 3 — Replay view: phase-sync instead of "play after the rep" (`src/engine/engine.js`, new `src/engine/phaseSync.js`)
- For actions whose rep rule is `type: 'angle'` (squat, curl, press, raise …): precompute once per
  action a table of the measured angle over the scripted half-cycle `pose(t)` for t ∈ [0, P/2]
  (sample `solve(pose(t))` + `angle3` on the rule's `show` joints).
- While a person is tracked and the recognised action has such a table, map the person's live angle
  (from the predicted camera skeleton) to the scripted phase t by table lookup, smooth it lightly, and
  render `pose(t)`. The figure then squats exactly when the person squats, with the clean scripted form.
- Fallback to the current queued replay (`RP.q`) for cycle/step actions (walk, jog, jacks, wave …)
  and when nobody is tracked.
- Counting is unchanged (still driven by FIT events).

### Step 4 — Docs, checks, log
- Update the camera notes in README/CLAUDE where they describe live/replay behaviour (Chinese).
- `npm run lint`, `npm run build`; smoke test in headless Chromium with a synthetic squat video if
  feasible (measure figure knee-angle vs. landmark knee-angle delay before/after).
- Append to `.dev_log`; commit on `claude/project-thread-c1dndn`, open a draft PR.

## Not touched
- `src/pose/fit.js` (verbatim upstream port), `CamPreview.vue` (PR #1).
- Model stays `pose_landmarker_full` (lite model is not in `public/mediapipe/`; can be a follow-up if
  CPU fallback machines are still slow).

## Risks
- Prediction overshoots on sudden stops/direction changes (bounded by the 150 ms cap and speed clamp).
- Higher One Euro cutoffs show a bit more jitter when standing still; beta keeps it low at rest.
- Phase sync only covers angle-rule actions; others keep the rep-queued replay.
